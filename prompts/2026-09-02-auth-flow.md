## §1 — the evaluation: Cognito vs Auth.js, probed by doing

**RECOMMENDATION: Auth.js v5 with Google, in-app. Cognito rejected for v1.**
The lead's prior was Cognito for stack coherence. I built both, and the single
technical argument that would have carried Cognito — the vault seam — turned out
not to exist. Evidence below; the lead overrules on the parts I weight wrong.

### The prize question is answered, and the answer dissolves it

The brief called this "the prize": *does Cognito's `sub` slot cleanly into the
workload-identity `--user-id` the vault already keys on?* It does. So does
everything else. `GetWorkloadAccessTokenForUserId` treats `--user-id` as an
**opaque string**, not an identity it verifies:

| user id handed to the vault | result |
|---|---|
| Cognito `sub` shape (bare uuid) | **MINTED** (token len 1812) |
| Cognito pool-qualified `us-east-1_x:uuid` | **MINTED** (1848) |
| Auth.js style `user_01K4TEST…` | **MINTED** (1799) |
| Google `sub` (21-digit numeric) | **MINTED** (1786) |
| a bare email address | **MINTED** (1780) |
| a user id that has never existed anywhere | **MINTED** (1815) |
| 128 characters | **MINTED** |
| 129 characters | refused — `ValidationException` |
| empty | refused |

That last-but-two row is the one that matters: **the vault mints a token for a
person who does not exist.** It is a partition key, not an authenticator. So
Cognito earns *zero* points at the seam the brief expected to decide this, and
one thing follows that belongs in §4 of the agents file: **the security boundary
is our session, not AgentCore.** Whoever our route says the reader is, is who
the vault hands Drive and Calendar tokens for. That is already true today of the
claim check, and it stays true after sign-in — which is exactly why sign-in has
to be right.

Hard limit for the contract: **user id ≤ 128 chars**, and lane X's connect route
already validates `^[A-Za-z0-9-]{8,64}$`. Both Google's `sub` (21 digits) and a
Cognito `sub` (36-char uuid) pass unchanged. **An id with an underscore or a
colon would not** — so the published contract stays inside `[A-Za-z0-9-]`, and
no prefixing scheme sneaks in later.

### (a) Cognito — built for real, not read about

Pool `us-east-1_b5mMC1Nws` (`govblock-auth-probe`, ESSENTIALS tier), app client
with secret, managed-login domain `govblock-probe`, Google registered as a
federated IdP with **Brendan's real client id and secret**, a real user, and
real tokens out of `ADMIN_USER_PASSWORD_AUTH`. Setup was genuinely fast — the
pool, domain and client took **~3 seconds of API calls**, and the AWS-standard
lean is not wrong about that part.

What the tokens actually are: `sub` = `6428d4b8-1071-70ca-4e91-33e22392dab3`
(36 chars), id token **1077 B**, access **1066 B**, refresh **1777 B** —
**3,920 B of cookie** if a session carries all three. Refresh tokens last 30
days; id/access default to 1 hour.

**The finding that decides it.** I followed Cognito's own Google button all the
way to Google, and Google refused:

```
redirect_uri=https://govblock-probe.auth.us-east-1.amazoncognito.com/oauth2/idpresponse
→ accounts.google.com/signin/oauth/error?authError=…redirect_uri_mismatch
```

So Cognito needs a Brendan console click too — and **the URI it needs is tied to
the Cognito domain name, not to ours.** Auth.js needs
`https://policy.nysgpt.com/api/auth/callback/google` — our own domain, which
does not move. Same one click either way; one of them is permanent and one of
them is hostage to a resource name.

**And the design constraint the brief set, which Cognito cannot meet.** §2 says
the /auth surface is "in the site's own design vocabulary — port, don't invent."
Social federation *must* traverse Cognito's hosted UI; there is no API-direct
Google path. Screenshot `cognito-hosted-ui.png` at 1714 px is a grey card on
`govblock-probe.auth.us-east-1.amazoncognito.com`. In fairness: **Managed Login
v2** has a real branding designer and would look far better than what I
captured (my domain defaulted to v1). It is still a redirect off
policy.nysgpt.com onto an Amazon host, and it is still not our components. With
Auth.js the reader stays on our page and only leaves for Google itself.

### (b) Auth.js v5 — built and compiled against our actual versions

Not read about either: a real Next **16.2.6** / React **19.2.4** app with
`next-auth@5.0.0-beta.32`, a Google provider, a `[...nextauth]` route and an SSR
page calling `auth()`.

- **It installs with no peer conflict** — its peers are `next: ^14 || ^15 || ^16`,
  `react: ^18.2 || ^19`.
- **`next build` succeeds with type-checking on** — 3 routes, no type errors.
  That matters more here than usual: our Amplify build **gates on type errors**
  and the local hook blocks `tsc` by name, so "does it compile" is a question
  that otherwise gets answered in production.

**The Amplify trap, checked in the shipped source rather than the docs.**
`origin.ts` already records that the Lambda thinks it is `localhost:3000` and
only forwarded headers carry the real host. Auth.js would have walked into
exactly that. It does not: `@auth/core/lib/utils/env.js:81` reads
`x-forwarded-host ?? host`, and `next-auth/lib/env.js` lets `AUTH_URL` override
the request URL outright. **Two independent fixes, one of them a single env
var** (`AUTH_URL=https://policy.nysgpt.com`). Belt and braces on the one
platform behaviour that has already bitten this codebase once.

**The honest mark against it:** `next-auth`'s `latest` dist-tag is still
**4.24.15**. v5 has been in beta for **33 releases since 2023-10-24** — two years
and nine months. That is not a labelling quibble and I am not going to wave it
away. It is also, measurably, what a very large share of Next.js production apps
run. I weight it as a real risk that is mitigated by the shape of the
integration, not by optimism: the whole surface is one route, one config file
and one accessor. If v5 ever breaks us, the blast radius is `lib/auth/**`.

### SSR under the buffering / 30 s ceiling — measured, and it is not close

| | Cognito id token (`aws-jwt-verify`, JWKS) | Auth.js JWE cookie (`jose`, local) |
|---|---|---|
| cold | **177.4 ms** (JWKS fetch) | **1.4 ms** |
| warm p50 / p95 | 0.056 / 0.089 ms | 0.054 / 0.149 ms |
| cookie weight | **3,920 B** (3 tokens) | **225 B** (1 cookie) |
| refresh in SSR | network call when the 1 h token expires | none for 30 days |

Warm, they are identical and both free. The differences are the **177 ms cold
JWKS fetch on a fresh Fluid/Lambda instance**, and the **refresh round trip**:
Cognito's IDP endpoint answers in **65–78 ms** from here and would be faster
in-region. Neither threatens the 30 s ceiling and I will not pretend they do.
What is real is that Auth.js's identity path makes **no network call at all**,
and on a surface whose agents already spend 12–40 s of that budget, the session
costing zero of it is worth having.

### Sharing one Google client between sign-in and the Drive/Calendar grant

The brief asked me to name this plainly: **split them, and the reason is blast
radius, not tidiness.**

Sharing works — I confirmed the vault's callback is already registered on
Brendan's client, and adding a second redirect URI to the same client is one
field. The upside is real: one consent screen, one verification submission, one
app name the reader sees. But today that secret lives in **exactly one place —
AgentCore's vault, inside AWS.** Auth.js needs the client secret in **our
Amplify environment** to exchange the code. Sharing one client therefore takes a
credential that has never left AWS and copies it into app config, where a
compromise reaches *both* sign-in and every reader's Drive and Calendar grants,
and where rotating it breaks both surfaces in the same instant.

A second Google OAuth client for sign-in costs Brendan about ninety seconds in a
console he is already in. It keeps the vault's secret in the vault, and it means
the sign-in credential can be rotated without touching anybody's stored grants.
**This is the one place I am recommending more setup rather than less, and it is
the only place.**

### Why Auth.js wins, in one paragraph

Cognito's case rested on the vault seam and it turned out the vault does not
care. What is left is: a hosted UI that cannot be our design and sends readers
to an Amazon host; a Google redirect URI hostage to a Cognito resource name; four
AWS resources and a client secret to keep instead of one route and two env vars;
3.9 KB of cookie against 225 B; and a 177 ms cold JWKS fetch we do not need. Its
one genuine advantage — a real user store with email sign-up, verification,
password reset and MFA for free — lands on stage 1's *second* item, and there is
a better answer for it: **§14 is already building double-opt-in email
verification on Resend, and an Auth.js magic link is the same machinery.** One
verified-address mechanism serving both sign-in and agent delivery beats two.

**Where I would happily be overruled:** if the lead weights the Google secret's
home more heavily than I do, the hybrid is **Auth.js with Cognito as the OIDC
provider** — Cognito keeps the users and the Google secret, Auth.js keeps the
session small and the surface ours. It costs the second redirect hop and the
domain-tied URI, and it is a strictly bigger v1. I do not recommend it, but it
is the coherent Cognito answer if Cognito is wanted.

### The user-id contract, proposed (lane X consumes it; nobody edits across)

```ts
// apps/web/lib/auth/user-id.ts
export type Identity =
  | { kind: "user"; id: string }    // signed in; id = `u-${google sub}` … see below
  | { kind: "browser"; id: string } // signed out; the claim check, unchanged
export async function identify(request?: Request): Promise<Identity>
```

One accessor, server-side, returns the string that goes to the vault's
`--user-id` and keys inbox threads, connections and tasks. Constraints it
guarantees, all measured tonight: matches `^[A-Za-z0-9-]{8,64}$` (lane X's
route already enforces this), never empty, ≤128 chars, and **stable across
sign-outs** so a returning reader finds their connections. Signed-out callers
keep getting today's claim check verbatim, so nothing lane X has shipped changes
behaviour until a reader actually signs in. Shape goes to the lead for the seam
agreement before I publish it.
