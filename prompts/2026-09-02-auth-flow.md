## §1 — the evaluation: Cognito vs Auth.js, probed by doing

**RECOMMENDATION: Auth.js v5 with Google, in-app. Cognito rejected for v1.**
The lead's prior was Cognito for stack coherence. I built both, and the single
technical argument that would have carried Cognito — the vault seam — turned out
not to exist. Evidence below; the lead overrules on the parts I weight wrong.

### The prize question is answered, and the answer dissolves it

The brief called this "the prize": *does Cognito's `sub` slot cleanly into the
workload-identity `--user-id` the vault already keys on?* It does. So does
everything else. `GetWorkloadAccessTokenForUserId` treats `--user-id` as an
**opaque string**, not an identity it verifies:

| user id handed to the vault | result |
|---|---|
| Cognito `sub` shape (bare uuid) | **MINTED** (token len 1812) |
| Cognito pool-qualified `us-east-1_x:uuid` | **MINTED** (1848) |
| Auth.js style `user_01K4TEST…` | **MINTED** (1799) |
| Google `sub` (21-digit numeric) | **MINTED** (1786) |
| a bare email address | **MINTED** (1780) |
| a user id that has never existed anywhere | **MINTED** (1815) |
| 128 characters | **MINTED** |
| 129 characters | refused — `ValidationException` |
| empty | refused |

That last-but-two row is the one that matters: **the vault mints a token for a
person who does not exist.** It is a partition key, not an authenticator. So
Cognito earns *zero* points at the seam the brief expected to decide this, and
one thing follows that belongs in §4 of the agents file: **the security boundary
is our session, not AgentCore.** Whoever our route says the reader is, is who
the vault hands Drive and Calendar tokens for. That is already true today of the
claim check, and it stays true after sign-in — which is exactly why sign-in has
to be right.

Hard limit for the contract: **user id ≤ 128 chars**, and lane X's connect route
already validates `^[A-Za-z0-9-]{8,64}$`. Both Google's `sub` (21 digits) and a
Cognito `sub` (36-char uuid) pass unchanged. **An id with an underscore or a
colon would not** — so the published contract stays inside `[A-Za-z0-9-]`, and
no prefixing scheme sneaks in later.

### SSR under the buffering / 30 s ceiling — measured, and it is not close

| | Cognito id token (`aws-jwt-verify`, JWKS) | Auth.js JWE cookie (`jose`, local) |
|---|---|---|
| cold | **177.4 ms** (JWKS fetch) | **1.4 ms** |
| warm p50 / p95 | 0.056 / 0.089 ms | 0.054 / 0.149 ms |
| cookie weight | **3,920 B** (3 tokens) | **225 B** (1 cookie) |
| refresh in SSR | network call when the 1 h token expires | none for 30 days |

Warm, they are identical and both free. The differences are the **177 ms cold
JWKS fetch on a fresh Fluid/Lambda instance**, and the **refresh round trip**:
Cognito's IDP endpoint answers in **65–78 ms** from here and would be faster
in-region. Neither threatens the 30 s ceiling and I will not pretend they do.
What is real is that Auth.js's identity path makes **no network call at all**,
and on a surface whose agents already spend 12–40 s of that budget, the session
costing zero of it is worth having.

### Sharing one Google client between sign-in and the Drive/Calendar grant

The brief asked me to name this plainly: **split them, and the reason is blast
radius, not tidiness.**

Sharing works — I confirmed the vault's callback is already registered on
Brendan's client, and adding a second redirect URI to the same client is one
field. The upside is real: one consent screen, one verification submission, one
app name the reader sees. But today that secret lives in **exactly one place —
AgentCore's vault, inside AWS.** Auth.js needs the client secret in **our
Amplify environment** to exchange the code. Sharing one client therefore takes a
credential that has never left AWS and copies it into app config, where a
compromise reaches *both* sign-in and every reader's Drive and Calendar grants,
and where rotating it breaks both surfaces in the same instant.

A second Google OAuth client for sign-in costs Brendan about ninety seconds in a
console he is already in. It keeps the vault's secret in the vault, and it means
the sign-in credential can be rotated without touching anybody's stored grants.
**This is the one place I am recommending more setup rather than less, and it is
the only place.**

### Why Auth.js wins, in one paragraph

Cognito's case rested on the vault seam and it turned out the vault does not
care. What is left is: a hosted UI that cannot be our design and sends readers
to an Amazon host; a Google redirect URI hostage to a Cognito resource name; four
AWS resources and a client secret to keep instead of one route and two env vars;
3.9 KB of cookie against 225 B; and a 177 ms cold JWKS fetch we do not need. Its
one genuine advantage — a real user store with email sign-up, verification,
password reset and MFA for free — lands on stage 1's *second* item, and there is
a better answer for it: **§14 is already building double-opt-in email
verification on Resend, and an Auth.js magic link is the same machinery.** One
verified-address mechanism serving both sign-in and agent delivery beats two.

**Where I would happily be overruled:** if the lead weights the Google secret's
home more heavily than I do, the hybrid is **Auth.js with Cognito as the OIDC
provider** — Cognito keeps the users and the Google secret, Auth.js keeps the
session small and the surface ours. It costs the second redirect hop and the
domain-tied URI, and it is a strictly bigger v1. I do not recommend it, but it
is the coherent Cognito answer if Cognito is wanted.

### The user-id contract, proposed (lane X consumes it; nobody edits across)

```ts

  | { kind: "user"; id: string }    // signed in; id = `u-${google sub}` … see below
  | { kind: "browser"; id: string } // signed out; the claim check, unchanged

```

One accessor, server-side, returns the string that goes to the vault's
`--user-id` and keys inbox threads, connections and tasks. Constraints it
guarantees, all measured tonight: matches `^[A-Za-z0-9-]{8,64}$` (lane X's
route already enforces this), never empty, ≤128 chars, and **stable across
sign-outs** so a returning reader finds their connections. Signed-out callers
keep getting today's claim check verbatim, so nothing lane X has shipped changes
behaviour until a reader actually signs in. Shape goes to the lead for the seam
agreement before I publish it.

### The inherited code did not compile in this repo

The stage-1 start that survived the session cut was correct in every way except
one it could not have known about. `next build` with type-checking on:

```
./lib/auth/config.ts:41:43
Type error: The inferred type of 'auth' cannot be named without a reference to
'../../../../node_modules/next-auth/lib'. This is likely not portable.
```

`.npmrc` sets **`node-linker=hoisted`**, so `next-auth` lives in the repo-root
`node_modules` rather than `apps/web`'s — four levels up, outside the package,
and TypeScript refuses to write that path into a declaration. The probe app that
proved "next build succeeds with type-checking on" was standalone, so its
`node_modules` was *inside* the package and the same code compiled. The
evaluation's measurement was true and its conclusion did not carry to this repo.

Fixed by naming the type instead of inferring it:

```ts
const nextAuth = NextAuth({ … })
export const handlers: NextAuthResult["handlers"] = nextAuth.handlers
export const auth: NextAuthResult["auth"] = nextAuth.auth   // …and signIn, signOut
```

Recording it because of where it would otherwise have landed: **Amplify gates the
build on type errors and the local hook blocks `tsc` by name**, so the first
report of this would have been a red deploy. The lesson generalises past this
lane — in a hoisted workspace, any library whose factory returns a type living in
an unexported subpath needs an explicit annotation, and only a real build in the
real repo finds it.

One more of the same kind, cheaper: `auth` is overloaded (server component /
middleware / route handler), so `Awaited<ReturnType<typeof auth>>` resolves to
the **middleware** overload and `null` is not assignable to `NextMiddleware`.
Name `Session | null` outright.

### The header affordance is a client component, and the number is 117

§2 asked for the account affordance on the header's right side. The obvious
`await auth()` in `SiteHeader` is wrong here, and the cost is measurable rather
than theoretical: `auth()` reads cookies, a cookie read in the **root layout**
opts every route that layout wraps into dynamic rendering, and this build
prerenders **117 pages**.

| build | prerendered | dynamic |
|---|---|---|
| before this lane | 117 | the API routes, `/agents*`, `/connectors`, `/calendar/[view]/[date]`, `/preview/*` |
| after `/auth` | **117** | + `/auth`, `/api/auth/[...nextauth]` |
| after the header affordance | **117** | unchanged |

So all 117 static pages would have become per-request Lambda renders on Amplify
**to draw one avatar**. PPR is the feature that lets a static shell hold a
dynamic hole; this app has no `cacheComponents` in `next.config.ts`, and turning
it on is a whole-app change and not mine to make. The session therefore comes
over the wire from Auth.js's own `/api/auth/session`.

**The cost of that, stated rather than buried** (house rule): one small GET per
hard page load, hitting the function instead of the CDN. `sessionStorage` makes
every later load in a tab paint from cache and client-side navigation does not
remount it, so it is roughly one request per visit. Signed-out is the *first*
paint — it is the common case and the truth until proven otherwise, so the usual
reader sees no skeleton and nothing shifts. If traffic ever makes it matter, the
cheap fix is a non-httpOnly hint cookie set at sign-in so signed-out readers
never fetch at all. Not worth building before anyone has signed in.

### The user-id contract — PUBLISHED. Final shape: `u-${google sub}`

`apps/web/lib/auth/contract.ts` — **imports nothing**, so the config that mints
an id and the accessor that hands it out both depend on it and neither can drift
from it. `apps/web/lib/auth/user-id.ts` re-exports all of it, so lane X still has
one import site:

```ts
import { identify, USER_ID_PATTERN, USER_ID_PREFIX, isUserId } from "@/lib/auth/user-id"

export type Identity =
  | { kind: "user"; id: string }     // signed in;  id = `u-${google sub}`
  | { kind: "browser"; id: string }  // signed out; the claim check, unchanged

export async function identify(claimCheck?: string | null): Promise<Identity | null>
```

Guarantees, as approved: `^[A-Za-z0-9-]{8,64}$`, never empty, ≤128 hard (64
binds, it is the tighter limit), stable across sign-outs, signed-out callers get
today's claim check verbatim.

**Confirming the final shape as `u-` + subject, and it turns out the prefix is
load-bearing in a way I had not seen when I proposed it.** I had it as
convenience for §3's merge — read a key, tell a person from a browser. Building
`identify()` found the real reason, and it is a security one:

> `identify()` takes the claim check **on the caller's word**. That is safe only
> because a claim check is 122 bits of randomness nobody can guess. **A Google
> `sub` is not that** — it is stable for a person across every app they sign
> into, so it is knowable by parties who are not that person. If signed-in ids
> and browser-minted ids shared one namespace, a caller who sent someone's user
> id *as their claim check* would be handed that person's Drive and Calendar
> grants. The vault would mint it without a murmur — it mints for people who do
> not exist.

So `identify()` refuses a claim check shaped like a user id:

```ts
if (!USER_ID_PATTERN.test(browser)) return null
if (isUserId(browser)) return null // a user id is not a bearer token
```

Without the prefix that check has to guess — "is this all digits?" — and rests on
Google never changing a format it documents only as an opaque string. Two
characters buy it by construction. Note this is a **guard, not a hole being
opened**: nothing is exploitable today because no user id exists yet, and the
guard is in place before the first one does.

Two more decisions inside the contract, both stated so lane X can object:

- **`userIdForSubject()` returns `null` rather than reshaping.** Google's `sub`
  is documented as opaque, up to 255 chars; today it is ~21 digits. A subject
  that breaks the charset or the length must not be quietly rewritten, because a
  rewritten id is a *different* id and a reader whose id silently changes loses
  every grant they made. The sign-in fails visibly instead.
- **Account linking is not solved and I am not pretending it is.** When email
  sign-in lands (§14's Resend machinery), the same human arriving by magic link
  gets a different id from their Google id. That is a real question for stage 2
  and it belongs to the lead, not to a quiet decision in this file.
